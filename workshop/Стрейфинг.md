**Да, все перечисленные метрики реально посчитать внутри локально запущенной Workshop-карты.** Для этого не нужен выделенный сервер и не нужно парсить демку: локальная карта в CS2 всё равно запускает игровую серверную логику, а скрипт карты может слушать выстрелы, получать владельца оружия и скорость его player pawn.

Но есть принципиальное разделение:

> **Посчитать данные внутри карты — относительно просто.**  
>  **Автоматически передать их в Android-приложение — отдельная и более сложная задача.**

## **Как карта получит каждую метрику**

В актуальном `cs_script` API есть события выстрела, доступ к игроку, его вводу и мировой скорости. В частности, карта может использовать `OnGunFire`, получить владельца оружия и вызвать у player pawn `GetAbsVelocity()`. API также позволяет проверять нажатия `LEFT/RIGHT`, запускать код по игровым тикам и сохранять данные аддона.

| Нужные данные | Как получить |
| ----- | ----- |
| 50 попыток | Обычный счётчик в скрипте |
| Чередование влево/вправо | Чётные попытки — влево, нечётные — вправо |
| Начало движения | Проверять `A/D` или скорость игрока каждый tick |
| Появление цели | Включить/переместить target после начала движения |
| Момент первого выстрела | Событие `OnGunFire` |
| Стрелявший игрок | `weapon.GetOwner()` |
| Скорость при выстреле | `player.GetAbsVelocity()` |
| Корректный stop-shot | Сравнить горизонтальную скорость с порогом |
| Результат слева/справа | Два отдельных счётчика |
| Средняя скорость | Сумма скоростей / число попыток |
| Попадание по цели | `OnBulletImpact` или событие damage |
| Итоговый экран | `game_text`, world text или собственные map entities |

Официальные обновления CS2 продолжают расширять map scripting API; например, в июле 2026 года Valve добавила новые callbacks и методы работы с оружием.

## **Логика одной попытки**

У карты будет небольшая state machine:

WAITING  
→ игроку показано направление  
→ игрок начал двигаться  
→ появилась цель  
→ ожидается первый выстрел  
→ зафиксирована скорость  
→ зафиксировано попадание/промах  
→ показан короткий feedback  
→ следующая попытка

Условный TypeScript-подобный код:

let attempt \= 0;  
let attemptActive \= false;  
let shotRecorded \= false;

let validShots \= 0;  
let speedSum \= 0;

let leftAttempts \= 0;  
let leftValid \= 0;

let rightAttempts \= 0;  
let rightValid \= 0;

const TOTAL\_ATTEMPTS \= 50;  
const STOP\_THRESHOLD \= /\* значение протокола \*/;

Instance.OnGunFire(({ weapon }) \=\> {  
    if (\!attemptActive || shotRecorded) return;

    const player \= weapon.GetOwner();  
    if (\!player) return;

    const velocity \= player.GetAbsVelocity();

    // Вертикальная скорость не нужна.  
    const horizontalSpeed \= Math.sqrt(  
        velocity.x \* velocity.x \+  
        velocity.y \* velocity.y  
    );

    shotRecorded \= true;  
    speedSum \+= horizontalSpeed;

    const direction \= attempt % 2 \=== 0 ? "left" : "right";  
    const valid \= horizontalSpeed \<= STOP\_THRESHOLD;

    if (direction \=== "left") {  
        leftAttempts++;  
        if (valid) leftValid++;  
    } else {  
        rightAttempts++;  
        if (valid) rightValid++;  
    }

    if (valid) validShots++;

    finishAttempt({  
        horizontalSpeed,  
        direction,  
        valid  
    });  
});

Это не готовый production-код, но архитектурно механизм именно такой.

## **Как определить движение влево и вправо**

Есть два подхода.

Первый и наиболее простой для MVP — **зафиксировать направление взгляда игрока** и чередовать инструкции:

Попытка 1: нажми A  
Попытка 2: нажми D  
Попытка 3: нажми A

Скрипт проверяет соответствующий input. Если игрок нажал неправильную клавишу, попытка не засчитывается.

Второй, более универсальный способ — вычислять направление движения относительно взгляда игрока:

1. получить `GetEyeAngles()`;  
2. построить локальный right-vector;  
3. спроецировать velocity на этот vector;  
4. знак результата покажет движение влево или вправо.

Для первого прототипа это избыточно. Фиксированная камера и стандартизированный коридор дадут более воспроизводимый тест.

## **Важная поправка к метрике**

Я бы не называл попытку просто «корректной», смешивая остановку и попадание.

Нужно хранить отдельно:

Stop quality:  
скорость в момент первого выстрела

Aim result:  
попадание или промах

Возможны четыре ситуации:

| Остановка | Попадание | Интерпретация |
| ----- | ----- | ----- |
| Хорошая | Да | Чистое выполнение |
| Хорошая | Нет | Movement нормальный, ошибка aim |
| Плохая | Да | Попадание несмотря на движение |
| Плохая | Нет | Смешанная ошибка |

Если считать «корректным» только попадание после остановки, score начнёт смешивать counter-strafing и aim. Тогда вы не сможете понять, какой навык реально изменился.

Для первой версии итог должен выглядеть так:

Stop-shots: 38 / 50  
Средняя скорость первого выстрела: 29 u/s

Влево: 18 / 25  
Вправо: 20 / 25

Попадания первым выстрелом: 34 / 50

## **Где взять порог корректной остановки**

Это не следует выбирать интуитивно.

Нужно создать версионируемый протокол:

diagnostic\_type: counter\_strafe  
protocol\_version: 0.1  
weapon: AK-47  
stop\_threshold: N units/sec  
attempts: 50

Порог должен быть проверен экспериментально:

1. записать скорости при полной остановке;  
2. записать скорости при раннем выстреле;  
3. посмотреть, при какой скорости начинает систематически ухудшаться точность;  
4. протестировать на игроках разного уровня;  
5. выбрать порог и не менять его внутри одной версии теста.

Иначе карта будет показывать точное число, основанное на произвольном нормативе.

## **Как показать результат игроку**

`DebugScreenText` предназначен для разработки, поэтому для опубликованной карты лучше использовать игровые entities:

* `game_text` для HUD;  
* `point_worldtext` для текста в комнате результатов;  
* отдельные панели и индикаторы.

`game_text` поддерживает изменение сообщения через `SetText` и последующий вывод на экран.

Финальный экран:

CYBERGYM COUNTER-STRAFE TEST

Результат: 76 / 100

Корректные stop-shots: 38 / 50  
Средняя скорость: 29 u/s

Влево: 72%  
Вправо: 80%

Слабая сторона: движение влево  
Код результата: CG1-38-29-18-20-K7

## **Можно ли сохранить результат внутри карты**

Да. В текущем scripting API существуют:

Instance.SetSaveData(data)  
Instance.GetSaveData()

Они позволяют сохранять строковые данные, связанные с конкретным Workshop-addon, и читать их при следующем запуске. Поэтому карта может хранить:

* лучший score;  
* историю последних тестов;  
* открытые уровни;  
* настройки;  
* baseline;  
* дату последней диагностики.

Например:

Instance.SetSaveData(JSON.stringify({  
    version: "counter-strafe-0.1",  
    completedAt: Date.now(),  
    validShots: 38,  
    totalAttempts: 50,  
    averageSpeed: 29.4,  
    leftValid: 18,  
    rightValid: 20  
}));

Но это **не означает**, что Android-приложение сможет прочитать эти данные.

## **Можно ли карте напрямую отправить результат в Supabase**

На данный момент я бы исходил из ответа: **нет, не стандартными средствами Workshop-карты**.

В публичном `cs_script` API нет задокументированного HTTP-клиента или метода типа:

fetch("https://api.cybergym.ru/result", ...)

Также в API не видно доступного метода получения SteamID, с помощью которого карта могла бы надёжно связать результат с аккаунтом CyberGym.

Поэтому такая архитектура нереалистична:

Workshop map  
→ напрямую HTTP  
→ Supabase

По крайней мере, пока Valve не добавит соответствующую возможность.

## **Реальные способы передать результат в приложение**

### **Вариант 1\. Ручной код — лучший для первой альфы**

Карта показывает короткий код:

CG1-38-294-18-20-K7

Где:

CG1  — версия протокола  
38   — valid stop-shots  
294  — средняя скорость × 10  
18   — successful left  
20   — successful right  
K7   — checksum

Пользователь вводит его в приложение. Приложение само разбирает поля.

Преимущества:

* не нужен desktop helper;  
* не нужны разрешения;  
* работает у любого подписчика Workshop;  
* реализация простая;  
* меньше ошибок, чем при вводе пяти отдельных чисел.

Checksum нужен не как защита от мошенничества, а чтобы обнаружить опечатку.

### **Вариант 2\. Скриншот результата**

Пользователь нажимает кнопку:

> Загрузить скриншот

Приложение распознаёт показатели или пользователь подтверждает их.

Это удобнее ручного заполнения, но OCR лучше делать после проверки базового цикла.

### **Вариант 3\. Desktop helper**

Отдельная программа на Windows:

Workshop map  
→ специальная строка в консоли  
→ локальный helper читает лог  
→ helper отправляет JSON в Supabase

Например, карта выводит:

CYBERGYM\_RESULT:  
{"protocol":"cs01","valid":38,"avgSpeed":29.4}

Helper отслеживает console log и отправляет результат.

Это технически правдоподобный путь, но потребуется отдельный proof of concept:

* стабильно ли результат попадает в лог;  
* можно ли включить логирование без сложного onboarding;  
* не меняется ли формат после обновлений;  
* как helper узнаёт аккаунт пользователя;  
* как обеспечить доверие и подпись результата.

### **Вариант 4\. Собственный сервер**

Наиболее надёжная автоматическая архитектура:

игрок подключается к серверу CyberGym  
→ серверный plugin собирает данные  
→ сервер сразу отправляет результат  
→ приложение получает результат автоматически

Преимущества:

* сервер знает SteamID;  
* можно отправлять HTTP-запросы;  
* результаты сложнее подделать;  
* можно строить benchmarks;  
* легко делать leaderboard.

Недостатки:

* серверная инфраструктура;  
* пинг;  
* стоимость;  
* поддержка;  
* пользователь не запускает карту полностью локально.

## **Что не поможет само по себе**

**FACEIT API** не видит локальные Workshop-сессии.

**Steam Web API** не отдаёт внутренние переменные карты.

**Game State Integration** не предоставляет произвольные custom metrics из вашего map script. Оно может помочь desktop helper понять, что запущена нужная карта, но не передаст `validShots` или `averageSpeed` само по себе.

**Сохранение через `SetSaveData`** позволяет карте помнить результат, но не создаёт API для Android.

## **Рекомендованная архитектура альфы**

1\. Карта считает всё локально.  
2\. Карта сохраняет результат для собственной истории.  
3\. Карта показывает итоговый экран.  
4\. Карта генерирует короткий result code.  
5\. Пользователь вводит код в Android.  
6\. Android декодирует и сохраняет данные в Supabase.

Так вы отделяете два риска:

Риск A:  
можем ли мы надёжно измерить counter-strafing?

Риск B:  
готов ли пользователь перенести результат в приложение?

Не стоит сначала разрабатывать desktop helper, пока не доказано, что сама диагностика и тренировочный цикл кому-то нужны.

## **Как я бы изменил первую Scrum-задачу**

Первой задачей должна быть не «сделать карту», а:

> Создать технический proof of concept, который в локальной Workshop-сессии фиксирует первый выстрел, получает горизонтальную скорость игрока, различает попытки влево и вправо и выводит результаты десяти попыток в консоль и на экран.

Критерии готовности PoC:

* событие первого выстрела фиксируется без дублей;  
* скорость соответствует визуально наблюдаемому движению;  
* полная остановка даёт близкие к нулю значения;  
* ранний выстрел даёт стабильно более высокие значения;  
* левая и правая попытки различаются;  
* повторный запуск не ломает state machine;  
* итог сохраняется через `SetSaveData`;  
* результат можно закодировать в короткую строку.

Только после этого стоит расширять тест до 50 попыток, делать дизайн и интеграцию с приложением.

Это именно тот инженерный риск, который нужно проверять отдельным минимальным тестом до расширения scope, как требует ваш протокол независимой оценки
